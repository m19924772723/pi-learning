## 一、章节核心要点（问题→机制）

1. **三层类型递进**：`pi-ai.Tool`（只需"向模型描述自己"：name/description/parameters）；`pi-agent-core.AgentTool`（需要"能被执行"：+label/prepareArguments/execute/executionMode）；产品层 `ToolDefinition`（还要"能被展示和扩展"：+promptSnippet/promptGuidelines/renderCall/renderResult，execute 多一个 ctx 参数）。分层理由：每层依赖范围独立，pi-ai 不应依赖 UI 渲染库。
2. **桥接包装器**：Agent Loop 只认识 AgentTool，产品层工具是 ToolDefinition，`wrapToolDefinition` 用闭包捕获 ctxFactory 注入第 5 个参数，Agent Loop 永远不知道 ExtensionContext 存在。
3. **五步管道**：LLM 的 ToolCall 不直接调函数，而是走 prepareArguments（兼容模型参数怪癖）→ validateToolArguments（TypeBox Schema 运行时校验）→ beforeToolCall（权限拦截，`{block:true, reason}` 可阻止）→ tool.execute（真正执行）→ afterToolCall（结果后处理，字段级覆盖合并）。前 3 步任何失败都不会执行工具。
4. **onUpdate 流式进度**：解决长任务黑盒；`acceptingUpdates` 标志位在 execute settle 后关闭，防止延迟孤儿回调污染已结束的调用；catch 里先 `await Promise.all(updateEvents)` 保证进度事件先送达再报错。
5. **一票否决式调度**：并行/串行不按工具对判断，只要批次中有一个工具声明 `sequential`（或全局配置强制），整批串行；并行也分三阶段——准备顺序（beforeToolCall 可能有副作用）、仅 execute 并行（Promise.all）、结果消息按调用顺序发送。
6. **错误即消息**：6 种错误（工具未找到、prepare 抛异常、Schema 失败、beforeToolCall 阻止、execute 抛异常、afterToolCall 抛异常）全部编码成 `isError:true` 的 ToolResultMessage，无异常穿透循环。原因：错误是给模型的反馈而非给框架的终止信号。
7. **两层错误处理**：工具内部主动识别已知错误并包装成具体描述（Bash 附"中止前输出+原因"、Read 附文件总行数），框架 catch 只做被动兜底、原样透传 `error.message`。
8. **Operations 抽象**：工具不直接调 `fs`/`child_process`，而是依赖最小化接口（ReadOperations/WriteOperations/EditOperations/BashOperations…），闭包捕获于创建时，测试可 Mock、远程可 SSH，工具代码零改动。

## 三、验证的关键结论

1. **五步管道真实存在且顺序与教程一致**：`prepareToolCall`（agent-loop.ts:607-675）内依次 prepareToolCallArguments（:624）→ validateToolArguments（:625）→ beforeToolCall（:626-654）；随后 `executePreparedToolCall`（:677-718）包住 tool.execute 并带 acceptingUpdates 闸门与 catch 兜底；最后 `finalizeExecutedToolCall`（:720-765）字段级合并 afterToolCall 结果（content/details/usage/terminate/isError，:745-752）。
2. **一票否决调度属实**：agent-loop.ts:417-419 用 `toolCalls.some(...executionMode === "sequential")` 判定，:420-423 分流顺序/并行；并行路径 :547-555 中 end 事件在 thunk 完成时发（乱序），但 ToolResultMessage 按 `orderedFinalizedCalls` 调用顺序生成。
3. **内置 7 工具均未声明 executionMode**：对 tools 目录 grep `executionMode` 仅命中 tool-definition-wrapper.ts 的透传——内置工具靠 `withFileMutationQueue`（file-mutation-queue.ts:32-61，按 realpath 键串行化同文件变更）做第二道防线。
4. **Bash 错误重包装 = "主动识别+原样兜底"**：bash.ts:351-358 识别 `"aborted"`/`"timeout:"` 并 appendStatus 包装；:363-365 非零退出码包装；:358 未识别异常 throw err 交给框架；框架兜底只透传 message（agent-loop.ts:712）。
5. **错误即消息的产物结构一致**：`createErrorToolResult`（agent-loop.ts:767-772）三行生成 `{content:[{type:"text",text:message}], details:{}}`；`createToolResultMessage`（:784-798）产出 `{role:"toolResult", toolCallId, toolName, content, details, usage, addedToolNames, isError, timestamp}`。

## 四、矛盾 / 漂移 / 疑问

- **行号漂移普遍且不均匀**：Tool +84；agent-loop 三函数 +45~49；read.ts 越界报错 :275→:137（-138，局部重构后更短）——以符号名为准。
- **本地新增字段教程未覆盖**：Tool 多 `constrainedSampling`（ai/types.ts:521）；AgentTool 多 `replay: "never"|"safe"`（agent/types.ts:403）；AgentToolResult 多 `addedToolNames`（:370）用于延迟工具加载。AgentTool 注释明言"抛异常而非在 content 里编码错误"（:395），与教程两层错误处理互为补充。
- **教程片段在本地有简化**：教程的 prepareToolCall 片段省略本地新增 abort 分支（agent-loop.ts:636-641、655-661）；wrapToolDefinition 本地签名加了 constrainedSampling 透传（tool-definition-wrapper.ts:14）。均向后兼容小幅演进。
