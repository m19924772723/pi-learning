## 一、章节核心要点（问题→机制）

1. **问题→三层架构**：同一段对话需翻译给 30+ 家 Provider（字段名、流式协议、思考参数、缓存标记四维全不同），Agent Loop 只有一行 `streamSimple()` 调用。解法拆三层：统一入口（查表路由）→ 事件协议（12 种统一事件）→ 翻译器（每家一种"方言"），前台与翻译员靠标准协议解耦。
2. **第一层 = 查表派活**：`model.api` 字符串当"工号"，从注册表（通讯录）查到对应翻译器后委托调用，入口层零业务逻辑。
3. **第二层 = 12 种统一事件**：内容分文字/思考/工具调用三类，每类"start→delta→end"三步 + 流开始/结束事件，且每事件携带 `partial: AssistantMessage` 快照（支撑"原地替换"逐字渲染）。
4. **第三层 = 翻译器 5 步骨架**：创建客户端→构建请求参数→发请求→处理响应流→发终止事件；第 2、4 步是上千行代码的根源。
5. **StreamFunction = "宪法"**：统一输入 (model, context, options)、统一输出 `AssistantMessageEventStream`、**错误不 throw 而 push error 事件**。
6. **ThinkingLevel 统一枚举 + 每家映射表**：上层只说 `reasoning: "high"`，翻译器查 `thinkingLevelMap`；不支持时 `clampThinkingLevel` 先向上找再向下找。
7. **缓存控制语义化**：`cacheRetention: none/short/long` 抽象，Anthropic 打 `cache_control` 便签、Bedrock 插 `cachePoint` 路标、OpenAI 发 `prompt_cache_key`（用 sessionId）。
8. **错误编码进流**：catch 里注入 `stopReason: aborted | error` 并 push error 事件；`isContextOverflow` 三重检测（错误消息模式 / token 对比 / length+零输出）兜底静默截断。

## 三、验证的关键结论

1. **"查表+派活"有实据**：`stream()` 内部 `resolveApiProvider(model.api)`（compat.ts:242-248，未注册直接 throw）→ `provider.stream(...)`（compat.ts:262-263）；`BUILTIN_APIS`（compat.ts:178-189）含 anthropic-messages / openai-completions / google-generative-ai / bedrock-converse-stream 等 10 个注册项。
2. **错误"编码进流"完全成立**：anthropic-messages.ts:811 `output.stopReason = options?.signal?.aborted ? "aborted" : "error"`，:813 `stream.push({ type: "error", reason, error })`；types.ts:331-332 注解明文把这条写成 `StreamFunction` 契约（"Error termination must produce ... via the stream protocol"）。
3. **思考模式双分支 + clamp 落实**：anthropic-messages.ts:1125-1148 同时存在 adaptive（:1138，配合 `output_config.effort`）与 budget（:1144-1146 `budget_tokens`）两种模式；`clampThinkingLevel` 在 7 个翻译器内调用（openai-responses.ts:222、google-generative-ai.ts:315 等），先向上 (models.ts:936-939) 再向下 (:940-943)。
4. **缓存三策略属实**：Anthropic 三处打点（消息块 1071/1078/1087、最后 user 消息 1384/1391、最后 tool 1459）；Bedrock 插独立 `cachePoint` 节点、long 级带 `ttl: ONE_HOUR`（bedrock-converse-stream.ts:879）；OpenAI Responses 用会话 id 当 key（openai-responses.ts:308 `prompt_cache_key ... options?.sessionId`）。
5. **coding-agent 消费端一致**：sdk.ts:3 从 `@earendil-works/pi-ai/compat` 导入 `streamSimple`，sdk.ts:37 `setDefaultStreamFn(streamSimple)` 设为默认，sdk.ts:324 `modelRuntime.streamSimple(model, context, {...})` 是实际调用点。

## 四、矛盾 / 漂移 / 疑问

- **ThinkingLevel 漂移**：教程六级 off/minimal/low/medium/high/xhigh；本地 types.ts:83-85 为 `minimal|low|medium|high|xhigh|max`（无 off，另有 `ModelThinkingLevel = "off" | ThinkingLevel`）；`EXTENDED_THINKING_LEVELS`（models.ts:913）7 值多一个 "max"。
- **done 事件 reason**：教程只列 stop/length/toolUse，本地 types.ts:559 还含 `"deferred"`。
- **compat 入口比教程复杂**：本地 `stream()` 派活前还有 `withEnvApiKey`（模型级 env key 注入，compat.ts:222-230）和 cloudflare 认证分支（compat.ts:257-259）。
- **images 翻译器分离**：教程称"10 种含 1 个 images 专用"；本地 BUILTIN_APIS 的 10 个全是 chat 流派，images 已独立为 images-api-registry.ts + providers/images/register-builtins.ts（compat.ts:25-29 导出），且新增 openai-codex/azure/mistral/google-vertex/pi-messages 等条目。
- **小疑问**：教程称 Anthropic 三处打点是"system 末尾 + 最后 tool + 最后 user"；本地 1071/1078/1087 位于消息数组（更接近 system/多段内容），1384/1391 才是最后 user、1459 是最后 tool——语义一致但对应关系需按本地行号重新映射。

## 五、一句话总结

教程四层断言（查表路由、12 事件协议、StreamFunction 契约、错误入流 + 统一枚举/映射表 + 缓存语义化）在本地 0.85.1 全部印证；仅 ThinkingLevel 新增 max、done 增加 deferred、images 注册表独立等少量版本漂移。
