## 一、章节核心要点（问题→机制）

1. **会话数据怎么存→两个正交子问题**："存哪里"（介质）与"长什么样"（结构）。coding-agent 选本地 JSONL 文件而非数据库（单用户本地 CLI、会话随 cwd 走、零依赖、可 grep 调试）；结构上放弃线性数组，选 **append-only 的 Session Tree**，使"回退/分支"从"删数据重写"变为"移动指针"，历史分支永不丢失。
2. **节点不可变→认父不认子**：每条 Entry 带 `id/parentId/timestamp`，只知父不知子；若父节点维护 children 列表，追加新子节点就须修改旧节点，违反 append-only，因此"认父不认子"是 append-only 的必要条件，配合 `byId` 映射表实现反向查询。
3. **追加=三步**：创建 Entry（parentId 指向当前 leafId）→ `byId.set` → `leafId = 新id`，O(1) 且不改任何旧节点。
4. **回退=一行**：`branch(fromId)` 仅做存在性检查后 `leafId = fromId`；再追加即自然分叉（分支=回退+追加的组合，非独立操作）。
5. **分支摘要可选**：`branchWithSummary` 在被抛弃分支位置挂一条 `branch_summary` 节点，LLM 生成结构化摘要（Goal/Progress/Decisions），当前路径的 Agent 得以"知道旧分支试过什么"而不被细节淹没。
6. **树→LLM 边界必须线性**：LLM API 只收 messages 数组，`buildSessionContext` 先把路径遍历（leaf→root 收集再 reverse），再按类型分派：消息进数组、model_change/thinking_level_change 覆盖式提取状态、元数据跳过。
7. **压缩的非破坏性**：`CompactionEntry` 记 `firstKeptEntryId`，遍历时跳过其之前的旧消息（不真删），回退到压缩点之前路径时旧消息自动复活；压缩只是"当前路径上的视图"。
8. **JSONL 行级追加 + 延迟写入**：新 Entry 直接 `appendFileSync`，与 append-only 契合；首次 assistant 消息到达前延迟写盘（flushed 标记），避免"有问无答"的半截对话，首次 flush 用 `openSync("wx")` 全量重写保证原子性。

## 三、验证的关键结论

1. **回退即移动 leafId，分叉数据完整保留**：`branch()` 只有存在性检查 + `this.leafId = branchFromId`（session-manager.ts:1374-1379），与教程伪代码一字不差；`_appendEntry` 内 byId.set + leafId=id 印证"追加三步、不改旧节点"（:1058-1063）。
2. **压缩是遍历期选择性收集而非删除**：`buildContextEntries` 以路径上最后一个 compaction 为界，仅保留 firstKeptEntryId 起的旧 entry 与 compaction 之后的 entry（session-manager.ts:441-453）；`CompactionEntry.firstKeptEntryId` 字段定义于 :72。
3. **延迟写入策略与教程四情况表吻合**：`_persist`（session-manager.ts:1029-1056）按 `hasAssistant && flushed` 分支：无 assistant 且未 flush 只置标记不写盘；有 assistant 未 flush 时 `openSync("wx")` 全量写 + 置 flushed；其余 appendFileSync。
4. **9 种 Entry 三组分类属实**：SessionEntry 联合（:144-153）正好 9 种，进上下文 4 种（message/custom_message/compaction/branch_summary）、影响状态 2 种（model_change/thinking_level_change）、元数据 3 种（custom/label/session_info）；sessionEntryToContextMessages（:383-408）按此分派。
5. **接口存在但 coding-agent 不复用仍属实**：本地 agent-core 抽象已更名重构（Storage/Session/SessionRepo，`packages/agent/src/harness/session/types.ts:455/530/592`），SessionManager（:856）确实未实现之，"两套独立实现平行存在"的结构性结论在本地依然成立。

## 四、矛盾 / 漂移 / 疑问

- ① **agent-core 层大重构（最主要漂移）**：教程 §七称 agent-core 有 11 种 Entry、SessionStorage 接口（harness/types.ts:440）、JsonlSessionStorage/InMemorySessionStorage 两实现。本地 packages/agent 这些符号全部不存在（grep SessionStorage|SessionEntry 于 packages/agent/src 得 0 命中），已重构为 `harness/session/` 下的 Storage+Session+SessionRepo 事务模型，Entry 仅 4 种（types.ts:16）。"9 vs 11 种"对比不再成立；该层在 0.85.x 已重写。
- ② **model 提取逻辑已变**：教程断言"assistant 消息不携带 model 信息，model 完全由 model_change 节点决定"。本地 getSessionContextSettings 新增规则：路径上 assistant 消息的 provider/model 也提取为 model 兜底（session-manager.ts:371-373），且 createAgentSession 会用它恢复模型（sdk.ts:200-204）。"model 仅由 model_change 决定"在本地已不严格成立。
- ③ **会话目录位置漂移**：教程称"每个项目的 `.pi/sessions/` 目录"。本地默认目录是全局 `~/.pi/agent/sessions/<encoded-cwd>/`（session-manager.ts:476-481，sdk.ts:134-135），cwd 编码进目录名实现"会话跟项目走"；机制同、落盘位置异（另有 --session/sessionDir 可显式指定）。
- ④ **branchWithSummary 签名变化**：教程伪代码为 `branchWithSummary(fromId): Promise<void>`（内部调 LLM 生成摘要）；本地为同步 `branchWithSummary(branchFromId, summary, details?, fromHook?, usage?): string`（session-manager.ts:1395-1420），摘要由上层 agent-session.ts 的 summarizeBranch（约 :3190-3286）先生成再传入。语义不变、接口迁移。
- ⑤ **疑问**：教程称会话文件在"项目目录下"、id 示例为 `a1b2c3d4` 短 ID；本地文件名为 `{timestamp}_{sessionId}.jsonl`（:949，sessionId 为完整 uuidv7），Entry 内才是 8 位短 id——教程未区分文件级 id 与 entry 级 id，属表述简化。

## 五、一句话总结

教程对 coding-agent 层（Session Tree、append-only、branch/buildSessionContext/延迟写入/9 种 Entry）的描述与本地 0.85.x 高度一致、可逐行对号入座；主要失真集中在 agent-core 层（已重构为 Storage/SessionRepo 模型，11 种 Entry 与旧接口名不复存在）及 model 提取、会话目录位置两处细节，另有 createAgentSession 入口迁移至 core/sdk.ts:173。
