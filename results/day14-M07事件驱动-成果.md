## 一、章节核心要点（问题→机制）

1. **问题**：外部要观察/干预 Agent，直接改内核源码会与上游冲突 → **发布-订阅**。Agent 只管 `emit`，不感知消费者；新增功能=挂一段自己的代码。
2. **两条管道**：10 种内核 `AgentEvent`（4 层嵌套生命周期：agent→turn→message→tool_execution，各层 start/update×N/end 配对）是"共同水源"；管道 A（`session.subscribe`，只读观察）与管道 B（扩展 `pi.on`，可拦截改写）都消费它。
3. **为什么 A 不能改行为、B 能？** 因果在"等不等 + 读不读返回值"：B 被 `await`（`_emitExtensionEvent` 带 await），A 不被等（`_emit` 是同步函数，返回值丢弃）——"能改"是"等+读返回值"的结果。
4. **执行前拦截 vs 开跑后广播**：`tool_call` 是扩展独占的"安检门"（执行前、能 `{block:true}` 短路、管道 A 收不到）；`tool_execution_start` 是内核发出的"已开跑广播"（拦不住、两管道都收）。另有 input/before_agent_start/context/tool_result 共 5 个决策点全归管道 B。
5. **高频工具进度攒批**：Bash 每行输出一个 update，逐个等会卡死 Agent → `executePreparedToolCall` 把 update 事件 promise 攒进数组，工具跑完统一 `await Promise.all`。
6. **三类派发**：通知型 `emit()`（串行 await + try-catch 隔离 + 忽略返回值）；决策型 `emitToolCall()`（await + 读返回值 + block 短路 + **无 try-catch**，fail-closed：扩展崩了宁可拦工具）；链式 transform 型（emitContext/emitToolResult/emitBeforeAgentStart/emitInput，上一个输出喂给下一个）。

## 三、验证的关键结论

1. **"对 B 等、对 A 不等"在源码上精确成立**：agent-session.ts:663 `await this._emitExtensionEvent(event)` vs :666 无 await 的 `this._emit(...)`；`_emit` 本体是同步函数（:586-590），`AgentSessionEventListener` 返回类型为 `void`（:188）。管道 B 被逐事件串行 await（runner.ts:861）。
2. **tool_call 的 fail-closed 是刻意设计且唯一裸奔**：runner.ts:982-1003 `emitToolCall` 无 try-catch，`block` 立即 return 短路（:995-996）；同文件 emit（:869）、emitToolResult（:957）、emitContext（:1050）、emitInput（:1272）、emitBeforeAgentStart（:1174）全部 try-catch + emitError 隔离。扩展在 tool_call 崩→异常冒泡→工具被拦（agent-session.ts:496-501 转成 "Extension failed, blocking execution"）。
3. **5 个决策点确实非内核 emit、由 SDK 主动触发**：tool_call/tool_result 挂 agent.beforeToolCall/afterToolCall（agent-session.ts:483,504）；input 在 sendUserMessage 流程 emitInput（:1156）；before_agent_start 在 agent.run 前（:1286）；context/provider 事件在 sdk.ts:365,348,356。管道 A 监听 `_emit` 所以收不到它们。
4. **工具进度 update 的"攒批"实现**：agent-loop.ts:682 建 `updateEvents: Promise<void>[]`，进度回调把 `emit({type:"tool_execution_update",...})` 的 promise 推入（:692-702），acceptingUpdates 置 false 后 `await Promise.all(updateEvents)`（:706,710）。
5. **内核层也存在同步屏障**：agent.ts:544-591 先 switch 更新内部状态，再 `for (const listener of this.listeners) await listener(event, signal)`（:588-590）。agent_end 的监听器仍在 run settlement 内（types.ts:427-429 注释明确）。

## 四、矛盾 / 漂移 / 疑问

- **行号漂移（正常）**：emitToolResult 872→927、emit() 796→851；tool_call 468→483、input 1131→1156、before_agent_start 1224→1286、sdk.ts context 350→365。符号全部可对上。
- **pi.on 重载数 30→33**：本地 types.ts 实测 33 个 `on(event: "..."` 重载——版本演进新增，属正常漂移。
- **一处需精确化的表述**：教程说"Agent 对 subscribe 不等"。严格说内核 `agent.subscribe` 的监听器是被 await 的（agent.ts:589），session 的 `_handleAgentEvent` 是其中一员（agent-session.ts:398 注册），它内部对管道 A 不 await。即"不等"发生在 session 层 `_handleAgentEvent`→`_emit` 这一段，不是内核层对 session 不等。教程 2.2 图示语境下正确，但直接读内核 processEvents 会误读——两层语义建议区分。
- **疑问（未深入）**：教程未解释 tool_call 钩子（agent-session.ts:482 构造期 `_installAgentToolHooks` 安装）与第 5 章五步管道中 beforeToolCall 步骤的先后关系，属教程留白而非矛盾。

## 五、一句话总结

第 7 章核心论断——"同源事件、两条管道，Agent 对扩展 pi.on 等并读返回值（可拦截改写，5 个决策点独占），对 session.subscribe 不等且返回值丢弃（只读观察）"——在本地 0.85.1 逐条成立，仅行号漂移与 pi.on 重载数（30→33）版本差。
